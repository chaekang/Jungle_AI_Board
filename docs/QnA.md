# Tripy 예상 QnA

1. 왜 MCP 서버를 따로 뒀나요? 그냥 AI 백엔드에서 함수로 호출하면 안 되나요?

   A: Agent 로직과 도구 로직을 분리하려고 썼다. 게시글 검색, 날씨 조회, 댓글 조회를 독립 도구로 관리하면 나중에 도구 추가/교체가 쉽다. 다만 규모가 작으면 함수 호출도 가능하고, MCP는 확장성을 고려한 선택이었다.

2. 왜 RAG를 썼나요? 그냥 LLM에게 물어보면 안 되나요?

   A: LLM만 쓰면 우리 서비스의 실제 게시글 데이터를 모른다. 트리피는 사용자 후기를 기반으로 추천해야 하므로, 관련 게시글을 먼저 검색하고 그 내용을 context로 넣는 RAG 구조가 필요했다.

3. 왜 LangChain을 안 쓰고 직접 RAG를 구현했나요?

   A: RAG는 LangChain이 아니라 구조다. 이번 프로젝트는 chunk 저장, embedding, pgvector 검색, context 전달 흐름이 명확해서 직접 구현하는 게 오히려 단순하고 제어하기 쉬웠다.

4. 왜 pgvector를 썼나요? 전용 벡터 DB를 쓰지 않은 이유는요?

   A: 게시글, 댓글, 지역, 예산 같은 서비스 데이터가 이미 PostgreSQL에 있으므로 같은 DB 안에서 벡터 검색과 일반 필터링을 같이 처리할 수 있었다. 규모가 더 커지면 Pinecone, Qdrant 같은 전용 벡터 DB도 고려할 수 있다.

5. 왜 키워드 검색이 아니라 임베딩 검색이 필요한가요?

   A: 키워드 검색은 단어가 정확히 맞아야 잘 찾는다. 하지만 "조용한 여행"과 "한적한 코스"처럼 표현이 달라도 의미가 비슷한 경우가 있다. 임베딩 검색은 이런 의미 기반 검색에 유리하다.

6. 왜 Agent 구조가 필요한가요? 단순 API 호출 순서로도 되지 않나요?

   A: 단순 추천이면 API 순서 호출도 가능하다. 하지만 이 서비스는 검색, 상세 글, 댓글, 날씨 정보를 모아서 답변해야 하므로 Agent가 도구 호출 흐름을 관리하게 했다. 현재는 정해진 흐름에 가깝고, 이후 도구가 늘어날 때 확장하기 좋다.

7. 왜 AI 백엔드를 기존 백엔드와 분리했나요?

   A: 기존 백엔드는 게시글, 회원, 댓글 같은 서비스 API를 담당하고, AI 백엔드는 LLM 호출, RAG, Agent 흐름을 담당한다. 역할을 분리하면 장애나 비용, 배포 단위를 나눠 관리하기 쉽다.

8. HttpOnly Cookie를 쓰면 끝인가요? CSRF는 어떻게 하나요?

   A: HttpOnly Cookie는 XSS로 토큰이 탈취되는 위험을 줄여준다. 다만 쿠키 기반 인증은 CSRF도 고려해야 하므로 SameSite 설정, CORS 제한, 필요하면 CSRF 토큰을 같이 적용해야 한다.

9. Rate Limit은 어디에 걸었고, 기준은 뭔가요?

   A: 반복 요청이 서버 부하와 AI 비용으로 이어질 수 있는 지점에 적용했다. 특히 로그인, AI 요청 같은 API가 대상이다. 실제 운영에서는 IP, 사용자 ID, API 종류별로 제한 정책을 다르게 가져가야 한다.

10. AI 답변이 틀리거나 없는 정보를 지어내면 어떻게 막나요?

   A: 관련 게시글, 댓글, 날씨 정보를 먼저 검색해서 context로 넣고, 답변 화면에 참고 게시글과 도구 사용 기록을 보여준다. 완전히 막을 수는 없지만, 근거 데이터를 제한하고 출처를 보여줘서 신뢰도를 높이는 방식이다.

# StudyTube 발표 대비 Q&A 및 아키텍처 설명 자료

## 1. 프로젝트 한 줄 설명과 기획 의도

### Q. 이 프로젝트를 한 문장으로 설명하면 무엇인가요?

StudyTube는 YouTube 강의를 단순히 저장하는 게시판이 아니라, 좋은 강의를 학습 코스로 묶고 AI 요약, 번역 자막, 전사문, 추천을 붙여 다른 사람과 공유할 수 있게 만든 AI 학습 게시판 서비스입니다. 핵심은 "무엇을 어떤 순서로 공부할지"를 영상 기반으로 정리해주는 것입니다.

### Q. 왜 일반 게시판이 아니라 YouTube 학습 코스 게시판으로 잡았나요?

개발 공부를 할 때 좋은 YouTube 강의는 많지만, 초보자는 순서와 난이도를 고르기 어렵습니다. 그래서 단일 영상 추천보다 여러 영상을 코스처럼 묶고, AI가 요약과 자막을 제공하면 실제 학습 흐름에 더 도움이 된다고 봤습니다. 게시판 요구사항도 만족하면서 프로젝트 주제를 학습 경험에 맞게 확장할 수 있었습니다.

### Q. 사용자가 이 서비스에서 얻는 가장 큰 가치는 무엇인가요?

영상 링크만 모아두는 것이 아니라, 영상별 요약과 전체 전사문, 번역 자막, 플레이리스트 단위의 학습 흐름을 함께 볼 수 있다는 점입니다. 사용자는 "이 영상을 볼지 말지", "어디부터 복습할지", "다음에 무엇을 볼지"를 더 빠르게 판단할 수 있습니다.

## 2. 프로젝트 구조와 폴더 분리

### Q. 왜 최상위에 `siwon` 폴더를 두고 그 안에 서비스를 모았나요?

팀 레포 루트와 실제 서비스 코드를 분리하려고 했습니다. CI/CD, 배포 스크립트, 환경변수, Docker Compose 기준점을 `siwon` 하나로 잡으면 배포 범위가 명확해집니다. 루트에 여러 실험 파일이나 팀 공통 파일이 있어도 실제 서비스 배포는 `siwon` 폴더만 보면 되도록 한 구조입니다.

### Q. 왜 `web`, `api`, `ai`를 나눴나요?

세 영역은 역할과 런타임이 다릅니다. `web`은 React 화면, `api`는 인증/게시판/DB를 담당하는 NestJS 서버, `ai`는 자막/요약/번역처럼 Python 생태계가 편한 FastAPI 서버입니다. 이렇게 나누면 프론트, 일반 백엔드, AI 기능을 각각 독립적으로 개발하고 테스트할 수 있습니다.

### Q. 서버를 하나로 합치지 않은 이유는 무엇인가요?

AI 기능은 외부 API 호출, YouTube 자막 수집, 긴 처리 시간 때문에 실패하거나 느려질 가능성이 큽니다. 일반 API와 AI 서버를 분리하면 AI 서버가 실패해도 로그인, 게시판, 플레이리스트 같은 핵심 기능은 유지할 수 있습니다. 역할이 분리되어 장애 원인도 더 쉽게 찾을 수 있습니다.

### Q. `controller`, `service`, `repository`, `types`를 나눈 이유는 무엇인가요?

`controller`는 HTTP 요청과 응답을 담당하고, `service`는 비즈니스 로직을 담당합니다. `repository`는 저장소 접근을 맡고, `types`는 데이터 계약을 정의합니다. 이 구조 덕분에 권한 로직, DB 접근, API 라우팅이 섞이지 않고 테스트하기 쉬워졌습니다.

### Q. `memory-board.repository.ts`는 왜 있나요?

PostgreSQL이 준비되지 않은 개발 환경이나 테스트 환경에서도 같은 기능을 돌릴 수 있게 만든 fallback 저장소입니다. 정식 저장소는 PostgreSQL이지만, DB가 잠시 꺼져도 데모와 테스트를 완전히 멈추지 않게 하기 위한 안전장치입니다.

### Q. `video-asset`을 게시글과 분리한 이유는 무엇인가요?

게시글은 사용자가 등록한 학습 단위이고, 영상 자산은 자막, 번역, 요약, 전사문처럼 시간이 걸려 생성되는 결과물입니다. 게시글 수정과 AI 생성 상태는 생명주기가 다르기 때문에 `video-asset`으로 분리했습니다. 덕분에 `pending`, `processing`, `partial`, `ready`, `failed` 같은 상태를 따로 관리할 수 있습니다.

### Q. `scripts`, `docs`, `artifacts`, `logs`를 따로 둔 이유는 무엇인가요?

실행 코드와 운영 자료를 분리하기 위해서입니다. `scripts`는 로컬 실행과 EC2 배포, `docs`는 발표와 설계 문서, `artifacts`는 생성 결과물, `logs`는 실행 로그를 담습니다. 코드와 데모 자료가 섞이지 않아서 발표 준비와 배포 관리가 쉬워졌습니다.

### Q. 테스트 파일을 소스 가까이에 둔 이유는 무엇인가요?

NestJS 서비스, 컨트롤러, 매퍼처럼 단위가 명확한 코드는 구현 파일 옆에 spec을 두는 편이 수정할 때 같이 확인하기 쉽습니다. 기능을 고치면 관련 테스트를 바로 찾을 수 있어 회귀 버그를 줄이는 데 도움이 됩니다.

## 3. 기술 선택 이유

### Q. React를 선택한 이유는 무엇인가요?

영상 재생, 자막 표시, 플레이리스트, 검색, AI 결과 상태처럼 화면 상태가 자주 바뀌는 서비스라 컴포넌트 기반 React가 적합했습니다. Vite를 사용해 개발 서버와 빌드 속도도 빠르게 가져갔습니다.

### Q. Next.js를 사용하지 않은 이유는 무엇인가요?

이 프로젝트는 SEO나 서버 렌더링보다 학습 보드의 인터랙션이 핵심이었습니다. 백엔드는 NestJS로 이미 분리했기 때문에 Next.js의 서버 기능을 쓰기보다 Vite React로 단순하게 가져가는 것이 더 적합했습니다.

### Q. NestJS를 선택한 이유는 무엇인가요?

인증, 게시글, 댓글, 플레이리스트, 권한 검사, DB 접근처럼 서비스 백엔드 구조가 필요했습니다. NestJS는 controller/service/repository 패턴과 DI 구조가 명확해서 기능을 분리하고 테스트하기 좋았습니다.

### Q. FastAPI를 선택한 이유는 무엇인가요?

RAG, MCP, Agent, OpenAI 호출, YouTube 자막 처리처럼 Python AI 생태계와 잘 맞는 작업이 많았습니다. FastAPI는 HTTP API로 NestJS와 연결하기 쉽고, AI 전용 서버로 분리하기에도 가볍습니다.

### Q. NestJS와 FastAPI를 같이 쓴 기준은 무엇인가요?

서비스 상태와 권한은 NestJS, AI 계산과 외부 AI 도구는 FastAPI로 나눴습니다. NestJS는 게시판의 중심 백엔드이고, FastAPI는 AI 전용 엔진입니다. React는 NestJS만 호출하고 NestJS가 내부에서 FastAPI를 프록시합니다.

### Q. PostgreSQL을 선택한 이유는 무엇인가요?

사용자, 게시글, 댓글, 플레이리스트, 영상 자산은 관계가 많은 데이터입니다. 관계형 DB가 모델링에 잘 맞고, 트랜잭션과 조회 안정성도 좋습니다. 이후 RAG 검색을 위해 pgvector를 붙일 수 있다는 점도 장점이었습니다.

### Q. MongoDB나 단순 파일 저장을 쓰지 않은 이유는 무엇인가요?

단순 파일 저장은 관계 조회와 동시성 관리가 약하고, MongoDB는 유연하지만 이 프로젝트의 핵심 데이터는 관계형 구조에 더 가깝습니다. 사용자별 게시글, 플레이리스트의 postIds, 댓글, 영상 자산 상태를 안정적으로 묶기 위해 PostgreSQL을 선택했습니다.

### Q. pgvector를 도입한 이유는 무엇인가요?

RAG를 위해서는 텍스트 검색만으로는 부족한 경우가 있습니다. 사용자의 학습 목표와 의미상 가까운 게시글이나 요약을 찾기 위해 embedding vector 검색이 필요했습니다. 별도 vector DB를 두기보다 PostgreSQL에 pgvector를 붙여 운영 복잡도를 줄였습니다.

### Q. Docker Compose를 쓴 이유는 무엇인가요?

로컬에서 Web, API, AI, DB를 한 번에 띄워 실제 서비스 구조와 비슷하게 테스트하기 위해서입니다. 팀원이 같은 명령으로 개발 환경을 맞출 수 있고, 배포 전 통합 실행도 확인하기 쉽습니다.

### Q. AWS EC2를 선택한 이유는 무엇인가요?

이번 과제에 AWS 학습 목적이 있었고, EC2는 서버 실행, 포트, 보안 그룹, 환경변수, 배포 스크립트를 직접 경험하기 좋았습니다. Vercel이나 ECS보다 손이 많이 가지만, 인프라 흐름을 이해하는 데는 EC2가 적합했습니다.

### Q. ECS, Elastic Beanstalk, Vercel 대신 EC2를 쓴 단점은 무엇인가요?

자동 확장, 무중단 배포, 장애 복구를 직접 구성해야 합니다. 현재 구조는 학습과 데모에 적합한 시작점이고, 운영 서비스로 키운다면 ECS, ALB, RDS, S3, CloudWatch를 붙여 분리하는 것이 좋습니다.

## 4. 전체 아키텍처와 데이터 흐름

### Q. 전체 요청 흐름은 어떻게 되나요?

사용자는 React 화면에서 요청을 보내고, React는 NestJS API만 호출합니다. NestJS는 인증과 권한을 확인한 뒤 DB를 읽거나 FastAPI AI 서버에 요청을 프록시합니다. AI 서버가 만든 자막, 요약, 전사문은 영상 자산으로 저장되고 watch 화면에서 재사용됩니다.

```txt
사용자 브라우저
  |
  v
React + Vite + TypeScript
  - 학습 게시판 UI
  - 영상 등록/재생/플레이리스트
  - AI 요약, 자막, 추천 결과 표시
  |
  v
NestJS REST API
  - 인증/게시글/댓글/플레이리스트
  - PostgreSQL/pgvector 접근
  - FastAPI AI 서비스 프록시
  - video asset 준비 작업 오케스트레이션
  |
  v
FastAPI AI Service
  - RAG 검색
  - MCP 기반 YouTube lookup
  - Agent study-plan loop
  - YouTube captions, summary, translation
  - OpenAI-compatible LLM/embedding 연동
  |
  v
외부 서비스
  - YouTube oEmbed / Data API / timed-text / yt-dlp
  - OpenAI-compatible LLM / embedding model
```

### Q. 영상 등록 흐름은 어떻게 되나요?

사용자가 영상 URL을 등록하면 NestJS가 게시글을 먼저 저장합니다. 이후 영상 자산 준비 작업을 비동기로 시작해서 자막, 번역, 요약, 전사문을 준비합니다. 사용자는 게시글 저장을 오래 기다리지 않고, 준비된 결과는 나중에 watch 화면에서 읽습니다.

```txt
React 영상 URL 입력
  -> NestJS POST /posts
  -> 게시글 저장
  -> video asset 준비 job 시작
  -> FastAPI captions / summary 호출
  -> 결과를 video asset으로 저장
```

### Q. watch 화면 흐름은 어떻게 되나요?

watch 화면은 먼저 저장된 video asset을 조회합니다. 준비된 번역 자막, 요약, 전사문이 있으면 바로 보여주고, 부족한 구간이 있으면 필요한 구간만 생성하거나 상태 메시지를 표시합니다. 핵심은 재생 시점에 모든 AI 작업을 새로 하지 않는 것입니다.

```txt
React watch 화면 진입
  -> NestJS GET /posts/:postId/video-asset
  -> 준비된 translated captions / summary / transcript 우선 사용
  -> 없는 구간은 제한적으로 fallback 생성
  -> 사용자에게 준비 중/부분 완료/실패 상태 표시
```

### Q. AI 추천 흐름은 어떻게 되나요?

먼저 저장된 게시글과 요약을 RAG로 검색하고, 부족하면 MCP 방식으로 YouTube 정보를 조회합니다. Agent는 이 결과를 사용자의 학습 목표에 맞춰 코스 형태로 정리합니다. 단순 검색 결과가 아니라 학습 순서가 있는 추천을 만들려고 했습니다.

```txt
React 코스 찾기 요청
  -> NestJS /ai/* 프록시
  -> FastAPI RAG 검색
  -> 필요 시 MCP YouTube lookup
  -> Agent가 학습 코스 초안 생성
  -> React가 추천 결과 표시
```

### Q. 왜 영상 저장 시점에 자막과 요약을 미리 생성하나요?

재생 중 실시간 생성만 사용하면 구간 점프 때마다 사용자가 기다려야 하고, 실패도 눈에 잘 보입니다. 저장 시점에 미리 준비하면 watch 화면에서는 저장된 자산을 빠르게 읽을 수 있습니다. 초기 준비 비용은 있지만 재생 경험이 훨씬 안정적입니다.

### Q. 실시간 생성 방식과 사전 생성 방식의 장단점은 무엇인가요?

실시간 생성은 저장 비용이 적고 필요한 구간만 처리할 수 있지만, 느리고 외부 API 실패가 바로 사용자 경험에 영향을 줍니다. 사전 생성은 초기 비용과 저장 공간이 필요하지만, 재생 시점에는 빠르고 일관된 결과를 보여줄 수 있습니다.

### Q. AI 기능이 실패해도 서비스가 멈추지 않게 어떻게 설계했나요?

AI 결과를 게시글과 분리된 video asset 상태로 관리했습니다. 자막이나 요약이 실패해도 게시글과 플레이리스트는 계속 사용할 수 있습니다. asset 상태를 `pending`, `processing`, `partial`, `ready`, `failed`로 나눠 일부 결과만 있어도 화면이 동작하게 했습니다.

### Q. 공개 게시판과 내 학습 코스 권한은 어떻게 나눴나요?

공개 게시물과 공개 플레이리스트는 로그인 사용자가 읽을 수 있게 했고, 수정/삭제/자산 재준비 같은 변경 작업은 작성자만 가능하게 했습니다. 읽기와 쓰기 권한을 분리해서 공유 기능과 보안을 동시에 만족시키려 했습니다.

## 5. AI 기능 구현 질문

### Q. AI 기능은 프로젝트에서 정확히 어떤 역할을 하나요?

AI는 크게 세 가지입니다. 첫째, 영상 자막과 요약을 만들어 학습 자료를 보강합니다. 둘째, RAG로 저장된 학습 자료 중 사용자 목표와 가까운 자료를 찾습니다. 셋째, Agent가 RAG와 MCP 결과를 조합해 학습 코스 초안을 만듭니다.

### Q. RAG, MCP, Agent를 왜 굳이 분리했나요?

역할이 다르기 때문입니다. RAG는 내부에 저장된 지식을 검색하는 기능이고, MCP는 외부 YouTube 정보를 도구처럼 가져오는 인터페이스입니다. Agent는 목표를 보고 어떤 도구를 쓸지 결정하고 결과를 조합하는 실행 흐름입니다. 분리했기 때문에 검색 실패, 외부 API 실패, Agent 실패를 각각 처리할 수 있습니다.

### Q. MCP는 이 프로젝트에서 어떤 역할인가요?

YouTube 관련 외부 정보를 가져오는 도구 인터페이스 역할입니다. 서비스 내부 데이터만으로 부족한 경우 외부 영상 메타데이터를 조회하고, Agent나 추천 흐름에서 사용할 수 있게 연결했습니다.

### Q. Agent는 단순 API 호출과 무엇이 다른가요?

단순 API 호출은 입력 하나에 응답 하나를 받는 구조입니다. Agent는 사용자의 목표를 보고 필요한 정보를 찾고, RAG 결과와 외부 도구 결과를 조합해 학습 코스 형태로 정리합니다. 즉 결과를 만드는 과정이 더 목표 지향적입니다.

### Q. 영상 요약은 어떤 데이터를 기반으로 생성하나요?

가장 우선하는 데이터는 자막과 전사문입니다. 자막을 가져오지 못하면 제목, 채널명, 저장된 설명, 노트를 보조 정보로 사용합니다. 그래서 AI 요약이 항상 완벽하지는 않지만, 가능한 범위에서 학습 맥락을 제공합니다.

### Q. 영상 요약을 항상 한국어로 만든 이유는 무엇인가요?

서비스 대상이 한국어 학습자이기 때문입니다. 원본 자막이 영어든 자동 생성 자막이든, 복습 자료는 한국어로 통일해야 사용자가 비교적 일관된 경험을 얻을 수 있습니다.

### Q. 전체 전사문을 타임스탬프별로 나누되 긴 간격으로 묶은 이유는 무엇인가요?

자막 단위 그대로 보여주면 `00:04`, `00:08`처럼 너무 잘게 쪼개져 읽기 어렵습니다. 반대로 전체를 한 덩어리로 보여주면 복습 위치를 찾기 어렵습니다. 그래서 60초 단위로 묶어 전체 내용을 유지하면서도 탐색하기 쉽게 했습니다.

### Q. AI 응답 품질이 일정하지 않을 수 있는데 어떻게 보정했나요?

응답 형식을 섹션 구조로 제한하고, 실패하거나 비어 있는 경우 fallback 문구와 저장된 메타데이터 기반 요약을 사용했습니다. 또한 자막, 요약, 전사문을 한 번 생성하고 저장해서 같은 영상에서는 결과가 계속 바뀌지 않게 했습니다.

### Q. OpenAI API가 느리거나 실패하면 어떻게 대응하나요?

AI 기능을 필수 경로로 두지 않고 video asset 상태로 분리했습니다. 실패하면 `failed`나 `partial` 상태로 남기고, 게시글과 재생 화면은 가능한 범위에서 계속 동작하게 했습니다. 운영 단계에서는 재시도 큐와 캐시를 더 강화할 수 있습니다.

## 6. YouTube 자막과 429 대응

### Q. YouTube 자막 가져오기가 어려웠을 것 같은데 어떻게 해결했나요?

가장 어려운 부분이었습니다. 서버에서 YouTube 자막을 반복 수집하면 429 차단이 발생할 수 있고, 영상마다 기본 자막, 자동 자막, 자막 없음 상태가 다릅니다. 그래서 가능한 경우 기본 자막과 자동 자막을 우선 사용하고, 결과를 video asset으로 저장해 반복 요청을 줄이는 방향으로 설계했습니다.

### Q. 429 Too Many Requests는 왜 발생하나요?

YouTube가 서버 요청을 봇성 트래픽으로 판단하거나 요청량이 많다고 판단하면 차단합니다. 특히 클라우드 서버 IP에서 반복적으로 timed-text나 영상 페이지를 요청하면 더 쉽게 발생할 수 있습니다.

### Q. 쿠키, PO Token, 프록시 같은 선택지가 있었는데 어떻게 봤나요?

쿠키는 빠르게 시도할 수 있지만 계정 의존성이 있고 장기 운영에는 불안정합니다. PO Token은 더 명시적인 서버 수집 경로를 만들 수 있지만 생성과 관리 설계가 필요합니다. 프록시는 효과가 있을 수 있지만 비용과 품질 문제가 있습니다. 그래서 단기적으로는 기본/자동 자막 fallback과 저장 캐시를 사용하고, 운영 단계에서는 PO Token과 안정적인 프록시를 검토하는 방향이 맞다고 봤습니다.

### Q. 기본 제공 자막과 자동 생성 자막은 어떻게 다루나요?

기본 제공 자막을 우선 사용하고, 없으면 YouTube 자동 생성 자막을 시도합니다. 둘 다 실패하면 자막 기반 기능은 실패 상태로 두고, 제목/설명/저장된 노트 기반 요약으로 기능을 축소합니다.

### Q. 자막이 없는 영상은 어떻게 처리하나요?

자막과 전사문은 실패 상태로 두고, 가능한 메타데이터 기반 요약만 제공합니다. 사용자에게는 기능 전체가 멈춘 것처럼 보이지 않도록 게시글과 플레이리스트 기능은 유지합니다.

### Q. SRT 파일을 직접 내려받아 처리하는 방식은 어떤가요?

가능하면 좋은 방식입니다. 하지만 SRT를 내려받는 과정 자체도 YouTube 자막 접근 문제와 같은 차단을 받을 수 있습니다. 핵심은 어떤 방식으로 가져오든 한 번 가져온 자막을 저장하고 재사용해 반복 요청을 줄이는 것입니다.

### Q. 자막 수집 방식의 가장 큰 단점은 무엇이고 어떻게 완화했나요?

외부 서비스 정책에 영향을 많이 받는다는 점입니다. 이를 완화하기 위해 자막 결과를 저장하는 video asset 구조를 만들고, 실패해도 게시판 기능은 유지되도록 했습니다. 다음 단계에서는 작업 큐, 캐시, PO Token, 프록시 운영 정책이 필요합니다.

## 7. UX와 성능 관련 질문

### Q. 자막이 영상 프로그레스 바를 가리는 문제는 어떻게 해결했나요?

자막 위치를 플레이어 하단 UI와 겹치지 않게 조정하고, 프로그레스 바에 마우스를 올리면 자막이 살짝 올라가도록 반응형 위치 조정을 넣었습니다. 사용자가 seek bar를 클릭할 수 있어야 해서 자막보다 플레이어 조작성을 우선했습니다.

### Q. 자막이 한 번에 너무 많이 나오는 문제는 어떻게 해결했나요?

한 번에 표시할 문장량을 제한하고, 현재 재생 시간에 맞는 세그먼트를 중심으로 보여주도록 조정했습니다. 너무 긴 문장은 읽기 어렵고 화면을 가리기 때문에, 말 속도와 화면 공간 사이에서 균형을 잡았습니다.

### Q. 구간을 건너뛰면 자막 생성까지 시간이 걸리는 문제는 어떻게 봤나요?

구간 이동 때마다 실시간 생성하면 근본적으로 지연이 생깁니다. 그래서 저장 순간부터 전체 자막과 요약을 준비하는 사전 생성 방식으로 개선했습니다. 준비된 자산이 있으면 점프해도 바로 보여줄 수 있고, 없는 경우만 제한적으로 fallback합니다.

### Q. 요약이 자막보다 더 느린 이유는 무엇인가요?

요약은 단순 세그먼트 번역보다 더 긴 문맥을 읽고 구조화해야 합니다. 전체 전사문을 다룰수록 LLM 호출 비용과 시간이 늘어납니다. 그래서 요약도 저장 자산으로 관리해 한 번 만든 결과를 재사용합니다.

### Q. 플레이리스트가 비어 있으면 화면이 안 뜨는 문제는 어떻게 처리해야 하나요?

데이터가 없다는 것도 정상 상태로 보고 빈 상태 UI를 보여줘야 합니다. 빈 배열을 에러처럼 처리하지 않고, "아직 저장된 코스가 없음" 같은 안내와 등록 경로를 제공하는 방식이 맞습니다.

### Q. 로그인 후 화면이 안 넘어가는 문제는 어떤 원인이 될 수 있나요?

API 서버 주소, CORS, 인증 토큰 저장, 배포 환경변수, 서버 포트 문제 중 하나일 수 있습니다. 이 프로젝트에서는 프론트가 API를 호출하고 실패하면 `Failed to fetch`가 뜰 수 있어서, 브라우저 Network 탭과 API health endpoint를 함께 확인하는 방식으로 원인을 분리했습니다.

## 8. 보안과 인증

### Q. 데모 계정을 제거한 이유는 무엇인가요?

실제 서비스로 전환하기 전에는 누구나 들어올 수 있는 우회 로그인 경로를 없애야 합니다. 데모 로그인은 발표나 개발에는 편하지만 운영 서비스에서는 인증 우회가 될 수 있어서 제거했습니다.

### Q. API Key는 어디에 저장하나요?

프론트에 두지 않고 서버 환경변수에 저장합니다. 사용자는 NestJS API만 호출하고, 실제 OpenAI Key는 서버 내부에서 FastAPI 또는 API 서버가 사용합니다. 이렇게 해야 브라우저 번들에 키가 노출되지 않습니다.

### Q. 공개 게시물을 읽을 수 있으면 보안 문제가 없나요?

공개 게시판이라는 서비스 성격상 읽기는 허용합니다. 대신 수정, 삭제, 영상 자산 재준비 같은 변경 작업은 작성자만 가능하게 막았습니다. 읽기 권한과 쓰기 권한을 분리하는 것이 핵심입니다.

### Q. 다른 사람이 올린 공개 영상을 볼 수 있게 하면서 수정은 못 하게 어떻게 처리했나요?

상세 조회와 영상 자산 조회는 로그인 사용자에게 허용하고, `updatePost`, `deletePost`, `prepare video asset`은 소유자 검사로 제한했습니다. 같은 게시물이라도 read path와 write path의 권한을 다르게 둔 것입니다.

## 9. AWS 배포와 운영

### Q. AWS 배포 구조를 간단히 설명하면 어떻게 되나요?

EC2 한 대에서 React 정적 서버, NestJS API, FastAPI AI 서버, PostgreSQL을 실행하는 구조로 시작했습니다. 학습 목적상 EC2 안에서 프로세스와 포트, 환경변수, 보안 그룹을 직접 관리했습니다.

### Q. 프론트, API, AI 서버는 각각 어떤 포트에서 동작하나요?

로컬과 배포 환경 기준으로 프론트는 주로 `5173`, API는 `3000`, AI 서버는 내부 `8000` 계열에서 동작합니다. 외부에는 프론트와 API 접근에 필요한 포트만 열고, AI 서버는 내부 호출 중심으로 두는 것이 좋습니다.

### Q. 보안 그룹에서는 어떤 포트를 열어야 하나요?

SSH 접속용 `22`, 프론트 접속용 `5173`, API 접속용 `3000`이 기본입니다. 운영 서비스라면 `80`과 `443`으로 Nginx나 ALB를 앞단에 두고 내부 포트는 외부에 직접 열지 않는 구성이 더 좋습니다.

### Q. 환경변수는 로컬과 EC2에서 어떻게 관리하나요?

로컬은 `.env`와 `.env.example`로 필요한 값을 맞추고, EC2는 서버 내부 `.env`에 실제 값을 넣습니다. OpenAI Key 같은 민감 정보는 Git에 올리지 않고 배포 서버에서만 주입합니다.

### Q. 커밋/푸시 후 바로 배포되게 하려면 어떤 구조가 필요한가요?

GitHub Actions나 EC2 autodeploy 스크립트를 사용해 `git pull`, 의존성 설치, build, 서버 재시작을 자동화하면 됩니다. 이 프로젝트는 `scripts` 아래에 EC2 배포와 자동 배포를 위한 스크립트를 분리해 두었습니다.

### Q. 배포할 때마다 OPENAI KEY를 새로 넣어야 하나요?

아닙니다. 서버의 환경변수 파일에 한 번 저장해두고 배포 스크립트가 그 값을 유지하게 만들면 됩니다. 새 EC2를 만들거나 환경 파일을 삭제한 경우에만 다시 채워야 합니다.

### Q. 현재 EC2 단일 서버 구조의 단점은 무엇인가요?

서버 한 대에 Web, API, AI, DB가 같이 있어 장애 격리와 확장성이 부족합니다. 사용자가 늘어나면 AI 작업과 DB 부하가 같이 올라갑니다. 운영 단계에서는 RDS, S3, ECS, ALB, CloudWatch로 분리하는 것이 좋습니다.

### Q. 비용 모니터링은 어떻게 해야 하나요?

AWS Billing에서 비용을 주기적으로 확인하고 CloudWatch 결제 경보를 설정해야 합니다. 프로젝트 종료 후에는 EC2, EBS, RDS, 탄력적 IP 같은 리소스를 삭제해야 불필요한 비용이 생기지 않습니다.

## 10. 한계와 개선 방향

### Q. 지금 프로젝트에서 가장 큰 기술적 한계는 무엇인가요?

YouTube 자막 수집이 외부 서비스 정책과 차단에 영향을 많이 받는다는 점입니다. AI 기능 자체보다 자막 원본을 안정적으로 확보하는 것이 더 큰 운영 리스크였습니다.

### Q. 사용자가 많아지면 가장 먼저 병목이 생길 부분은 어디인가요?

AI 자막/요약 생성 작업입니다. 영상 하나에 대해 자막 수집, 번역, 요약, 전사문 생성이 필요하기 때문에 CPU, 네트워크, 외부 API 호출 비용이 먼저 병목이 됩니다.

### Q. 백그라운드 작업 큐를 본격적으로 만든다면 어떤 기술을 쓸 수 있나요?

NestJS 환경에서는 BullMQ와 Redis를 사용할 수 있고, AWS 쪽으로 가면 SQS와 worker 구조를 사용할 수 있습니다. 핵심은 현재 in-process job을 durable queue로 분리해 서버 재시작에도 작업이 사라지지 않게 하는 것입니다.

### Q. 운영 서비스라면 구조를 어떻게 개선할 건가요?

프론트는 S3/CloudFront 또는 Vercel로 분리하고, API와 AI는 컨테이너로 배포합니다. DB는 RDS, 자막과 요약 캐시는 S3나 DB에 저장하고, AI 작업은 큐와 worker로 분리합니다. 앞단에는 ALB나 Nginx를 두고 HTTPS를 적용합니다.

### Q. 발표 이후 가장 먼저 고치고 싶은 부분은 무엇인가요?

자막 수집 안정성과 작업 큐입니다. 사용자가 영상을 저장하는 순간 전체 자산 준비가 안정적으로 돌아가고, 실패하면 재시도할 수 있어야 실제 서비스 품질이 올라갑니다.

### Q. 이번 프로젝트에서 가장 어려웠던 점은 무엇인가요?

단순 게시판이 아니라 영상 재생, 자막, 번역, 요약, 저장 자산, 배포까지 연결해야 해서 실패 지점이 많았습니다. 그래서 상태를 쪼개고 fallback을 두면서 한 부분이 실패해도 전체 서비스가 멈추지 않도록 설계했습니다.

## 12. 발표에서 강조할 핵심 선택

1. React는 NestJS만 호출하고, NestJS가 FastAPI를 내부 프록시한다.
2. NestJS는 서비스 상태, 권한, DB 접근의 중심이다.
3. FastAPI는 AI 계산과 외부 AI 도구 연동에 집중한다.
4. 게시글과 video asset을 분리해 AI 생성 상태를 따로 관리한다.
5. 긴 영상 자막은 실시간 전체 번역이 아니라 prepared asset 중심으로 처리한다.
6. PostgreSQL + pgvector로 관계형 데이터와 RAG 검색을 함께 관리한다.
7. DB fallback은 정식 운영용이 아니라 개발과 발표 안정성을 위한 안전장치다.
8. 현재 EC2 단일 서버는 학습용 시작점이고, 운영 단계에서는 큐/스토리지/DB/서버를 분리해야 한다.
